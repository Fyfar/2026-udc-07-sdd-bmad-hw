- (constraint) types.ts shapes (Order, LineItem, Coupon) and pricing.ts signatures (lineTotalKopecks, subtotalKopecks, shippingKopecks, tierPercent) are frozen -- PRD S5 Non-Goals, app/AGENTS.md guardrail. New engine is additive-only, in a new file.
- (constraint) Money is integer kopecks end to end, no floats anywhere in the discount path -- app/AGENTS.md convention, PRD Glossary.
- (constraint) app/tsconfig.json has noUncheckedIndexedAccess:true -- any Record/Map bucket lookup types as T|undefined at every read site; the spine must pin a bucket representation that stays sound under this flag.
- (constraint) Tests must be named after the acceptance criterion they cover (app/AGENTS.md convention); npm test (vitest) and npm run typecheck (tsc --noEmit) are the delivery gate. No new runtime dependencies (app/AGENTS.md: 'no runtime dependencies').
- (event) Read app/src/types.ts, app/src/pricing.ts, app/src/index.ts, app/AGENTS.md, app/tsconfig.json, app/src/pricing.test.ts as an implementer, cross-checked against PRD FR-1..FR-6/FR-2a and epics.md Stories 1.1-4.2.
- (question) PRD FR-2 says codes are 'resolved... and validated independently before any discount math runs' (two-phase: validate-all, then apply-all). But FR-3's non-category-fixed-coupon proportional split reads each bucket's CURRENT (already-reduced) share, and FR-4's category_claimed reason depends on whether an EARLIER code was already APPLIED to that category. Neither can be decided without having already run the discount math for earlier codes. FR-2's 'independently... before any discount math' is literally incompatible with FR-3+FR-4 read together -- a real PRD self-contradiction, not just underspecification.
- (decision) AD-1: resolve the FR-2/FR-3/FR-4 conflict by rejecting the two-phase reading. The engine is a SINGLE left-to-right pass over order.coupons: for each entry, run its checks against the buckets/claimed-set/seen-set state as accumulated from EARLIER entries only, then if it passes, apply its bucket reduction immediately (updating buckets a later coupon's proportional split or category_claimed check will read) before moving to the next entry. 'Independently' in FR-2 is read narrowly as 'not merged/summed with other codes', not as 'computed from a frozen pre-state'.
- (question) FR-4 says category_claimed fires between two DIFFERENT codes scoped to the same category. But FR-2's stated precedence order is not_found -> expired -> min_not_met -> no_matching_items -> category_claimed -> duplicate. If a category-scoped coupon is entered twice (a duplicate), and occurrence 1 was applied (claiming the category), a literal reading has occurrence 2 hit category_claimed (its own category, now claimed) BEFORE it ever reaches the duplicate check -- contradicting Story 2.3's explicit requirement that a same-code repeat reports 'duplicate', not 'category_claimed'.
- (decision) AD-2: category_claimed's condition is 'this bucket's category was already claimed by an earlier APPLIED coupon whose normalized (trim+lowercase) code differs from this entry's normalized code.' A self-claim by a repeat of the same code is excluded from category_claimed and falls through to duplicate. This keeps FR-2's stated 6-step precedence order textually intact while matching FR-4's 'different codes' framing and Story 2.3's required output.
- (question) FR-2's fixed validation-order list (not_found -> expired -> min_not_met -> no_matching_items -> category_claimed -> duplicate) never places the FR-2a 'too_many_codes' cap check anywhere in it. FR-2a separately says codes past the cap are rejected 'without being checked against catalog/expiry/etc,' implying the cap runs before all six -- but this is never stated as part of FR-2's own ordered list, and epics.md Story 2.4 doesn't resolve it either.
- (decision) AD-3: too_many_codes is check #0, run before the FR-2 six-step list, based on the RAW 0-based index of the entry in order.coupons (index >= 10 is rejected), not on a count of distinct/deduplicated codes. This also resolves PRD FR-2a's internal wobble between 'distinct valid-looking codes' phrasing and 'the 11th and later entered codes' phrasing -- position in the raw array is the operative rule, since distinctness itself isn't known until codes are normalized and compared, which is more machinery than the cap needs.
- (decision) AD-4: the 'seen normalized codes' set used for duplicate detection is updated after EVERY processed entry (applied or rejected alike), keyed by trim+lowercase code string, and membership is checked before adding the current entry. This makes not_found/expired/min_not_met/no_matching_items fire identically for every occurrence of an unresolvable code (duplicate never masks those), matching Story 2.3 AC2's worked example.
- (question) Neither the PRD nor types.ts states whether Coupon.code is unique within the coupons: Coupon[] catalog array passed to the engine. PRD FR-2 Out-of-Scope only excuses percent-range/fixed-non-negative validation, not code-uniqueness.
- (decision) AD-5: catalog lookup takes the FIRST Coupon in array order whose normalized code matches; duplicate codes within the catalog itself are not detected or rejected -- out of scope per PRD's 'Coupon record well-formedness assumed guaranteed upstream', extended here to cover code-uniqueness too since it's the same category of upstream data-integrity assumption.
- (decision) AD-6: new code lives in one new file, app/src/discounts.ts (engine function + RejectionReason/CouponOutcome/DiscountResult types), with colocated app/src/discounts.test.ts -- mirrors pricing.ts's single-file, no-subfolder pattern. app/src/types.ts is untouched; app/src/index.ts gets additive re-exports only.
- (decision) AD-7: engine signature is applyDiscounts(order: Order, coupons: Coupon[], asOf: Date): DiscountResult -- asOf is REQUIRED, no default value on the function itself. This pins PRD FR-5's hedge ('Date (or ISO string)') down to Date only, and honors Story 1.2 AC2's explicit requirement that 'new Date()' defaulting happens only at the outer call site (index.ts / a checkout handler), never inside the pure engine function.
- (decision) AD-8: category buckets are represented as a Partial<Record<LineItem['category'], number>>, populated only for categories present in the order (per FR-3). Given tsconfig's noUncheckedIndexedAccess:true, every bucket read after the initial per-order setup must go through a narrow accessor that is non-null by construction (buckets are seeded for every present category before any discount step runs, and no step ever deletes a key) -- documented so implementers don't reach for non-null assertions ad hoc at every read site.
- (decision) AD-9: round-half-up on money in this engine maps directly to JS Math.round() with no wrapper -- every value rounded (bucket-reduction amounts, proportional shares) is non-negative at the point it's rounded (buckets and coupon values never go negative pre-floor), and Math.round()'s toward-+Infinity tie-break coincides with 'half up' for all non-negative inputs. No decimal/bignum library needed (also forbidden by app/AGENTS.md's no-new-runtime-deps rule).
- (assumption) Verified (not just assumed): with at most 3 category buckets -- LineItem['category'] is a fixed 3-value union standard|fresh|digital, and Non-Goals forbids changing types.ts, so this cap is durable -- the sum of independently half-up-rounded proportional shares of an integer fixed-coupon amount differs from the exact target by at most 1 kopeck in either direction. Hand-checked via the rounding-error-per-share bound (each share's rounding error is in (-0.5, +0.5], and the fractional parts of the 3 shares sum to an integer in {0,1,2}, capping |total error| at 1). This closes PRD's 'single leftover/shortfall kopeck' claim (FR-3, addendum B) as CORRECT for this domain rather than an unverified assertion -- it would need re-verification only if the category union ever grew past 3 values, which the Non-Goals guardrail currently forbids.
- (decision) AD-10: the tier discount's own effect never appears as an entry in the FR-6 per-code outcome list (that list is one entry per string in order.coupons only); the tier's effect is visible only via the aggregate discountedItemsTotal/grandTotal. A rejected coupon's outcome entry omits discountKopecks entirely (undefined, matching the '?' in its type) rather than reporting 0.
- (decision) Paradigm: functional core -- one pure exported function (applyDiscounts) that folds a fixed step sequence (tier, then each order.coupons entry in array order) over a local, non-exported accumulator {buckets, claimedCategories, seenCodes, outcomes}; no classes, no hidden module state, no I/O. Matches pricing.ts's existing pure (order) => value style with the accumulator kept as a local variable inside the one function (or a small set of private helpers it calls), never as a returned/shared mutable object.
- (event) spine finalized
- (decision) CouponOutcome.code echoes the ORIGINAL as-typed string from order.coupons (untrimmed, original case) -- not the normalized form -- so a checkout UI can match each outcome back to exactly the string the customer entered by array position/value. Normalization (trim+lowercase) is used only internally for catalog lookup, seenCodes, and claim comparisons.
