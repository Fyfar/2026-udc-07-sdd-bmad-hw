- (event) Headless/autonomous run (auto mode, no stakeholder available). Fast path: read feature-request.md + app/src/types.ts + app/src/pricing.ts + app/AGENTS.md, resolved every ticket ambiguity as an explicit decision instead of asking.
- (decision) Stacking order: tier % applied first to items subtotal, then coupon % applied to the tier-discounted remainder, then fixed-amount coupons subtracted last. Rationale: sequential (multiplicative) stacking protects margin better than additive, and mirrors checkout UX (loyalty is account-level/known before checkout, promo code is entered as the last step).
- (decision) Discount base: tier and coupon discounts apply only to the items subtotal (subtotalKopecks), never to shippingKopecks. Shipping stays the flat, already-specified fee.
- (decision) Category-scoped coupon: percent/fixed value is computed against the subtotal of matching-category line items only, not the whole order subtotal.
- (decision) minSubtotalKopecks check is evaluated against the order's gross item subtotal, before any tier or coupon discount is applied -- so applying tier first can never help a coupon meet its own minimum.
- (decision) Multiple coupons: every code the customer enters is validated independently (case-insensitive, trimmed, de-duplicated -- a repeated code applies once) and, if valid, all are applied together -- not just the best one.
- (decision) Same-category conflict: if two valid, unexpired coupons target the same category, only the first by entry order is applied; the rest are rejected with an explicit 'category already discounted' reason.
- (decision) Expired/invalid coupon handling: explicit rejection, not a silent no-op. Pricing result carries a per-code outcome (applied | rejected + reason) so checkout UI can tell the customer why a code did not apply.
- (decision) Rounding: round each line-level discount amount to the nearest whole kopeck (round-half-up) at the point it is computed, before summing -- never carry fractional kopecks forward. All amounts stay integer kopecks end to end.
- (decision) Floor: the discounted item subtotal cannot go below 0 kopecks. Shipping, when owed, is added after the floor and is never itself discounted.
- (assumption) 'Fixed' coupon value is stored/compared in kopecks via the existing Coupon.value field, even though the ticket describes it to the business reader in hryvnia -- no schema change needed, this is a display-layer concern only.
- (event) Left open (not resolved here, flagged for PM/architecture): (1) no cap on how many promo codes a customer may enter -- abuse/perf question; (2) whether the loyalty discount and each coupon should be individually itemized on the receipt/UI -- a UX decision, not a pricing-engine one.
